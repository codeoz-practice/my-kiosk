## 네, 정확한 지적입니다 — "session"이라는 개념이 잘못됐어요

제가 이전 답변에서 슬쩍 만든 `sessions` 테이블은 **"이용권"과 "실제 착석/이용"이라는 서로 다른 두 개념을 하나로 뭉뚱그린 것**이었습니다. 실제 도메인을 제대로 나누면 이렇게 됩니다.

- **이용권(Ticket/Pass)**: 사용자가 구매한 시간 그 자체. "잔여 시간"이라는 상태를 **여러 번의 방문에 걸쳐** 들고 있는 주체
- **이용 세션(Usage Session)**: 사용자가 한 번 앉아서 이용권의 잔여 시간을 **실시간으로 소비하는 단발성 이벤트**

즉, **시간은 이용권 단위로 흐르고, 세션은 그 흐름을 "지금 이 순간 재생 중인지"를 나타내는 재생 헤드(playhead) 같은 겁니다.**

---

## 왜 이 구분이 중요한가

PC방/스터디카페를 생각해보면 한 이용권으로 **여러 번 들어왔다 나갔다** 할 수 있죠.

- 10시간 이용권을 사서 → 오늘 3시간 쓰고 나감 → 내일 2시간 쓰고 나감 → 잔여 5시간 남음
- 이때 "잔여 시간"은 **이용권에 귀속**돼야지, 세션 하나에 귀속되면 안 됩니다. 세션은 끝나면 사라지는 일회성 기록이니까요.

만약 세션 하나에만 `end_at`을 박아두면, **이용권이라는 개념 자체가 증발**하고 "한 번 들어오면 그 세션이 끝날 때까지의 카운트다운"만 남습니다. 여러 번 나눠 쓰는 이용권 모델에서는 이게 성립하지 않아요.

---

## 올바른 스키마: 이용권 ↔ 세션을 분리

```sql
-- 이용권: 시간의 실제 소유자 (잔여 시간이 여기 산다)
CREATE TABLE tickets (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL,
  ticket_type VARCHAR(30) NOT NULL,       -- '10시간정액권', '1개월정기권' 등
  total_minutes INT NOT NULL,
  remaining_minutes INT NOT NULL,         -- 이게 유일한 '잔여 시간' 원천
  expires_at TIMESTAMPTZ,                 -- 정기권이면 만료일도 별도로 체크
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE', -- ACTIVE, EXHAUSTED, EXPIRED
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 세션: 한 번의 착석/입장 (이용권 잔여 시간을 실시간 소비 중인 상태)
CREATE TABLE usage_sessions (
  id UUID PRIMARY KEY,
  ticket_id UUID NOT NULL REFERENCES tickets(id),
  seat_id UUID,
  started_at TIMESTAMPTZ NOT NULL,
  planned_end_at TIMESTAMPTZ NOT NULL,    -- 시작 시점의 이용권 잔여시간으로 계산한 예정 종료시각
  ended_at TIMESTAMPTZ,                   -- 실제 종료 시각 (조기퇴실이면 planned_end_at보다 빠름)
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE', -- ACTIVE, ENDED
  bullmq_job_id VARCHAR(100)
);
```

**핵심**: `remaining_minutes`는 `tickets`에만 있고, `usage_sessions`는 그걸 "지금 얼마나 빌려서 쓰고 있는지"만 나타냅니다.

## 1단계: 세션 시작 — 이용권 잔여시간을 빌려온다

```javascript
async function startUsageSession(ticketId, seatId) {
  let sessionId, plannedEndAt;

  await db.transaction(async (tx) => {
    const { rows } = await tx.query(
      `SELECT remaining_minutes, expires_at, status FROM tickets WHERE id = $1 FOR UPDATE`,
      [ticketId]
    );
    const ticket = rows[0];

    if (ticket.status !== 'ACTIVE' || ticket.remaining_minutes <= 0) {
      throw new BusinessError('사용 가능한 잔여 시간이 없습니다');
    }

    sessionId = uuid();
    // 잔여시간 전체를 '이번 세션에서 쓸 수 있는 한도'로 설정
    plannedEndAt = new Date(Date.now() + ticket.remaining_minutes * 60 * 1000);

    // 정기권처럼 만료일이 따로 있다면, 둘 중 더 이른 시각으로 캡
    if (ticket.expires_at && ticket.expires_at < plannedEndAt) {
      plannedEndAt = ticket.expires_at;
    }

    await tx.query(
      `INSERT INTO usage_sessions (id, ticket_id, seat_id, started_at, planned_end_at, status)
       VALUES ($1, $2, $3, now(), $4, 'ACTIVE')`,
      [sessionId, ticketId, seatId, plannedEndAt]
    );
    // 주의: 여기서 remaining_minutes를 미리 차감하지 않습니다!
    // 아직 실제로 다 쓴 게 아니니까요. 정산은 세션 '종료' 시점에.
  });

  const delay = plannedEndAt.getTime() - Date.now();
  const job = await sessionQueue.add('SESSION_EXPIRE', { sessionId }, { delay, jobId: sessionId });
  await db.query(`UPDATE usage_sessions SET bullmq_job_id = $1 WHERE id = $2`, [job.id, sessionId]);

  return { sessionId, plannedEndAt };
}
```

> **왜 시작 시점에 잔여시간을 차감하지 않는가**: 세션이 예정보다 일찍 끝날 수도 있잖아요(조기 퇴실). 미리 다 차감해버리면 "실제로 쓴 시간"과 "차감된 시간"이 어긋납니다. **차감은 반드시 "실제 사용이 끝났을 때" 확정**해야 정확합니다.

## 2단계: 세션 종료 — 여기서 비로소 이용권 잔여시간이 깎인다

세션이 끝나는 경로는 세 가지입니다: **(a) 시간 다 써서 BullMQ 이벤트로 자동 종료, (b) 사용자가 조기 퇴실, (c) 관리자 강제 종료.** 셋 다 아래 로직 하나로 처리돼야 합니다.

아래는 실제 구현(Prisma, `src/usage-session/usage-session.repository.ts`)입니다. `endedAt`은 호출자가 넘긴 시각을 그대로 쓰고(테스트 용이성·정확성 목적으로 내부에서 `new Date()`를 새로 찍지 않음), BullMQ delayed job 제거는 이 레포지토리 메서드의 책임이 아니라 서비스 레이어에서 별도로 처리합니다.

```typescript
async endUsageSession(sessionId: string, now: Date): Promise<void> {
  await this.prisma.executeTransaction(async (tx) => {
    // FOR UPDATE는 Prisma Client API로 표현 불가 → raw query 필요
    const [session] = await tx.$queryRaw<
      { id: string; status: string; startedAt: Date; ticketId: string }[]
    >`
      SELECT us.id, us.status, us."startedAt", us."ticketId"
        FROM usage_session us
        WHERE id = ${sessionId}
        FOR UPDATE`;

    if (!session) throw new UsageSessionNotFoundError(sessionId);
    if (session.status !== UsageSessionStatus.ACTIVE) return; // 이미 종료됨 - 멱등 처리

    const endedAt = now;
    // 실제 소비한 시간을 '분 단위'로 정확히 계산 (반올림 정책에 따라 조정)
    const consumedMinutes = Math.ceil(
      (endedAt.getTime() - session.startedAt.getTime()) / 60000,
    );

    await tx.usageSession.update({
      where: { id: sessionId },
      data: { status: UsageSessionStatus.ENDED, endedAt },
    });

    // 이용권 잔여시간 차감 - 유일한 진실의 원천을 여기서 갱신
    await tx.$executeRaw`
      UPDATE ticket
      SET "remainingMinutes" = GREATEST(0, "remainingMinutes" - ${consumedMinutes}),
          status = CASE
            WHEN "remainingMinutes" - ${consumedMinutes} <= 0
            THEN ${TicketStatus.EXHAUSTED}
            ELSE status
          END
      WHERE id = ${session.ticketId}
    `;
  });
}
```

- **멱등성 체크(`if (session.status !== UsageSessionStatus.ACTIVE) return`)**: BullMQ 이벤트로 자동 종료된 직후, 사용자가 거의 동시에 "퇴실하기" 버튼을 눌러도 두 번 차감되지 않게 막아줍니다.
- **`FOR UPDATE` 락**: 세션 하나에 종료 요청이 동시에 들어오는 race condition 방지. Prisma Client API는 `FOR UPDATE`를 지원하지 않아 `$queryRaw`로 처리합니다.
- **`!session` 가드**: 존재하지 않는 `sessionId`로 호출되면 `undefined` 참조 에러 대신 `UsageSessionNotFoundError`를 명시적으로 던집니다.
- **`GREATEST` + `CASE WHEN`**: Prisma Client의 `update()`로는 "현재 DB 값을 기준으로 한 clamping + 조건부 분기"를 한 문장에 표현할 수 없어 `$executeRaw`가 필요합니다.
- **BullMQ job 제거**: 이 메서드는 티켓/세션 상태 정산만 책임지고, delayed job 취소는 호출하는 서비스 레이어에서 `reason`에 따라 처리합니다.

## 3단계: 남은 시간 조회 — 이용권과 세션을 합쳐서 계산

```javascript
async function getRemainingTime(ticketId) {
  const { rows } = await db.query(
    `SELECT t.remaining_minutes, t.status,
            s.id AS session_id, s.planned_end_at
     FROM tickets t
     LEFT JOIN usage_sessions s 
       ON s.ticket_id = t.id AND s.status = 'ACTIVE'
     WHERE t.id = $1`,
    [ticketId]
  );
  const row = rows[0];

  if (row.session_id) {
    // 지금 이용 중 -> 실시간으로 흘러가는 중이므로 planned_end_at 기준 계산
    const remainingMs = Math.max(0, new Date(row.planned_end_at).getTime() - Date.now());
    return { remainingMinutes: Math.ceil(remainingMs / 60000), inUse: true };
  } else {
    // 대기 중 -> 이용권에 저장된 값이 곧 잔여시간
    return { remainingMinutes: row.remaining_minutes, inUse: false };
  }
}
```

이게 지난 답변에서 놓쳤던 부분이에요. **"남은 시간"은 상태에 따라 두 가지 원천 중 하나를 봐야 합니다.**

| 상태 | 남은 시간의 원천 |
|---|---|
| 이용 중 (세션 ACTIVE) | `session.planned_end_at - now()` (실시간으로 줄어드는 중) |
| 대기 중 (세션 없음) | `ticket.remaining_minutes` (그대로 고정된 값) |

사용자든 관리자든 이 함수 하나만 호출하면 되고, 관리자는 여기에 권한 체크만 얹으면 됩니다.

## 정리: 개념 교통정리

```
이용권(Ticket) ── 시간 잔고의 진짜 주인, 여러 세션에 걸쳐 잔여시간을 들고 있음
    │
    ├── 세션1 (사용) → 종료 시 실제 소비시간만큼 이용권 잔고 차감
    ├── 세션2 (사용) → 종료 시 또 차감
    └── ...
```

- **시간은 이용권 단위로 흐르는 게 맞습니다.** 세션은 그 흐름 중 "지금 재생 중인 구간"을 나타내는 임시 상태일 뿐이에요.
- BullMQ delay는 **세션의 `planned_end_at`**에 걸어야 하고 (지난 답변의 로직 그대로), 그 이벤트가 발화하면 위 `endUsageSession(sessionId, 'EXPIRED')`를 호출해서 **이용권 잔고를 정산**하는 흐름으로 이어집니다.

## 시니어 관점 추가 인사이트

- 여러 세션에 걸쳐 이용권을 나눠 쓰는 구조에서는 **"동시에 같은 이용권으로 두 자리에 앉는" 경우를 반드시 막아야 합니다.** `startUsageSession` 호출 전에 `SELECT ... WHERE ticket_id = $1 AND status = 'ACTIVE'` 로 이미 활성 세션이 있는지부터 체크하세요. 그렇지 않으면 한 이용권으로 두 좌석을 동시에 점유하는 버그가 생깁니다.
- `consumedMinutes` 계산할 때 **초/분 단위 반올림 정책(올림 vs 내림 vs 반올림)**을 명확히 정해두세요. 이게 요금제 약관과 직결되는 부분이라 나중에 "왜 3분 덜 썼는데 5분 차감됐냐"는 CS로 이어지기 쉽습니다.

관련해서 궁금하실 만한 주제로, **"이용권에 남은 시간이 애매하게 적을 때(예: 2분 남음) 세션을 아예 시작 못 하게 막을지, 아니면 2분만 쓰고 자동 종료시킬지"** 같은 정책 설계도 실무에서 자주 고민하는 지점인데, 필요하시면 이어서 다뤄드릴게요.

## 티켓 타입 단일 테이블 통합 근거 정리
1. 생명주기·부가 기능이 타입 무관하게 완전히 동일하다
status 전이, orderItemId(1:1 주문 연결), usageSessions(세션 생성 플로우), pauses(일시정지) 모두 TIME/PERIOD 구분 없이 같은 코드 경로를 탑니다(usage-session.service.ts의 createSession이 타입별로 분기하는 지점은 "만료 예상 시간 계산" 한 곳뿐). 타입에 따라 달라지는 건 사실상 "잔여량을 어떻게 계산하는가"라는 계산 로직 하나뿐이고, 그 외 정체성·관계·인덱스는 전부 공유됩니다.

2. 혼합 리스트 조회가 실제 요구사항이다
ticket.repository.ts의 SORT_FIELD_MAP과 스키마 주석("사용자: 내 티켓 목록 만료일 가까운 순")을 보면, 시간권/정기권을 한 화면에서 만료 임박 순으로 섞어서 보여줘야 합니다. 타입별로 테이블을 쪼개면 이 정렬이 두 테이블 조인/UNION 없이는 불가능해지고, @@index([userId, expiresAt]) / @@index([userId, minuteExpireDeadline])처럼 단일 인덱스로 끝나는 지금 구조의 이점이 사라집니다.

3. 대안(부모+자식 테이블 분리)의 비용이 이득보다 크다
자식 테이블로 쪼개면 nullable 컬럼과 non-null assertion은 없앨 수 있지만, 대신 (a) 티켓 생성 시 부모+자식 2개 테이블 트랜잭션, (b) 조회 시 매번 조인, (c) 위 혼합 정렬 쿼리의 인덱스 활용 불가라는 대가를 치릅니다. 타입이 2개뿐이고 타입별 필드가 4~5개 수준인 규모에서는 이 비용이 실익을 넘어섭니다.

4. non-null assertion 문제는 이미 스키마가 아니라 코드 레벨에서 봉쇄되어 있다
ticket.expiresAt!, ticket.remainingMinutes! 같은 단언은 ticket.service.ts의 toTicketOutData 매핑 함수 한 곳에만 존재하고 스캐터되지 않았습니다. "분기 지점을 한 곳에 모은다"는 목적은 이미 달성된 상태이므로, 스키마를 바꾸지 않고도 assertDefined 같은 이미 쓰고 있는 타입가드 유틸로 런타임 체크를 명시화하면 충분합니다.

결론: TIME/PERIOD가 계산 로직에서 보이는 차이("소비형 vs 캘린더형")는 도메인적으로 실재하지만, 그 차이는 스키마 레벨(테이블 분리)이 아니라 코드 레벨(계산 메서드 분기)에서 흡수하는 게 맞는 위치입니다. 지금의 단일 Ticket 테이블 + discriminator(type) + nullable 타입별 컬럼 구조는 유지하는 것을 권장합니다.
