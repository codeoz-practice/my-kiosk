# 이용권/세션 시스템 설계 정리

## 1. 핵심 개념 구분

| 개념                         | 정의                                                                                   |
| ---------------------------- | -------------------------------------------------------------------------------------- |
| **이용권(Ticket)**           | 사용자가 구매한 시간/기간 잔고 그 자체. 여러 번의 방문에 걸쳐 잔여량을 들고 있는 주체  |
| **이용 세션(Usage Session)** | 사용자가 한 번 앉아서 이용권을 실시간으로 소비하는 단발성 이벤트 (재생 헤드 역할)      |
| **상품(Ticket Product)**     | 관리자가 정의하는 판매 메뉴 (시간권/정기권 등). 시간이 지나며 가격/조건이 바뀔 수 있음 |

**원칙**: 시간은 **이용권 단위**로 흐르고, 세션은 그 흐름 중 "지금 재생 중인 구간"을 나타내는 임시 상태일 뿐이다.

---

## 2. 원자성(Atomicity) 처리 — DB ↔ BullMQ(외부 시스템)

### 문제

DB 트랜잭션과 BullMQ(Redis)는 서로 다른 리소스라 진짜 분산 트랜잭션으로 묶을 수 없음.

- DB 커밋 후 BullMQ 실패 → 상태는 바뀌었는데 Job이 없음
- BullMQ 성공 후 DB 롤백 → 존재하지 않는 데이터로 워커가 동작

### 해결: Transactional Outbox 패턴

1. **DB 트랜잭션 안에서는 DB 쓰기만** 수행 (비즈니스 상태 업데이트 + `outbox_events` 테이블에 "발행 의도" insert)
2. **별도 relay 프로세스**가 outbox를 폴링하며 BullMQ에 실제 enqueue
   - `jobId`를 outbox event id로 고정 → 재시도돼도 중복 Job 생성 안 됨
   - BullMQ 호출 실패해도 outbox row는 `PENDING`으로 남아 다음 폴링에서 재시도 (at-least-once 보장)
3. **Job 처리 결과로 반영되는 DB 업데이트**는 워커 자신의 트랜잭션에서, **멱등성 체크**(`job_executions` 테이블 등)와 함께 수행

## 3. 남은 시간 계산 원칙

### 잘못된 접근

Redis(BullMQ Job)에서 남은 시간을 직접 조회 → **안티패턴**

- BullMQ는 조회용이 아니라 트리거용 시스템
- Job 상태(delayed/active/completed)에 따라 계산식이 달라져 예외 케이스 급증
- "진실의 원천"이 DB와 Redis 두 곳으로 쪼개짐

### 올바른 접근

**DB에 저장된 절대 시각을 유일한 원천으로 삼고, 조회 시점마다 파생 계산**

| 이용권 종류              | 잔여량 단위          | 계산 기준                                                                               |
| ------------------------ | -------------------- | --------------------------------------------------------------------------------------- |
| **시간권(TIME_BASED)**   | 분(minutes)          | 대기 중: `ticket.remaining_minutes` 그대로<br>이용 중: `session.planned_end_at - now()` |
| **정기권(PERIOD_BASED)** | 일(days) / 만료 시각 | `ticket.expires_at - now()` (세션과 무관하게 항상 동일 계산)                            |

- "남은 시간(minutes)" 저장 방식은 지양 — 반드시 **절대 시각**만 저장하고 나머지는 매번 재계산
- 사용자 조회 API와 관리자 조회 API는 **동일한 함수 재사용**, 권한 체크만 다르게

## 4. 이용권 시작/종료 흐름

### 세션 시작 (`startUsageSession`)

- **시간권**: 잔여 분만큼 `planned_end_at` 계산 → BullMQ에 delay job 등록 (자동 종료 트리거)
- **정기권**: 만료일 체크만 수행, `planned_end_at`/BullMQ 등록 없음 (소비 개념이 없으므로)
- 동일 이용권으로 동시에 두 자리 이용하는 것을 막기 위해 시작 전 활성 세션 존재 여부 체크 필요

### 세션 종료 (`endUsageSession`)

- **시간권**: 실제 소비 시간(`ended_at - started_at`)만큼 `tickets.remaining_minutes` 차감
- **정기권**: 세션 상태만 `ENDED`로 변경, **잔여량 차감 없음**
- 반드시 **멱등성 체크** (`status !== 'ACTIVE'`면 스킵) — 자동 종료와 수동 퇴실이 동시에 들어와도 이중 차감 방지
- `FOR UPDATE` 락으로 동시 종료 요청 race condition 방지

### 24시간 운영 — "영업 마감" 트리거가 없는 경우

정기권 세션 종료는 세 경로 중 하나로만 발생:

1. **사용자 스스로 퇴실** (가장 정상적인 경로)
2. **좌석 센서/하드웨어 감지** (있다면 가장 신뢰도 높음)
3. **장시간 무응답 안전망** (BullMQ 재활용) — 위 두 경로가 실패했을 때의 최후 방어선. 시간권의 delay와 달리 "정상 종료가 안 됐을 때만 발동하는 예외 처리용"

## 5. 테이블 설계

### `tickets` — 실제 발급된 개별 구매 건

```sql
CREATE TABLE tickets (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL,
  product_id UUID NOT NULL REFERENCES products(id),  -- 출처 추적용 FK

  -- 구매 시점 스냅샷 (상품 조건이 나중에 바뀌어도 절대 안 바뀜)
  product_name_snapshot VARCHAR(50) NOT NULL,
  purchased_price INT NOT NULL,
  total_minutes INT,          -- 시간권일 때만 값 존재
  remaining_minutes INT,      -- 잔여 시간의 유일한 원천 (시간권만 사용)
  expires_at TIMESTAMPTZ,     -- 정기권일 때 만료 시각

  category VARCHAR(20) NOT NULL,  -- 'TIME_BASED' | 'PERIOD_BASED'
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### `products` — 판매 상품(메뉴) 정의

```sql
CREATE TABLE products (
  id UUID PRIMARY KEY,
  name VARCHAR(50) NOT NULL,
  category VARCHAR(20) NOT NULL,
  total_minutes INT,          -- 시간권 전용, nullable
  period_days INT,            -- 정기권 전용, nullable
  price INT NOT NULL,         -- 현재 판매가 (계속 바뀔 수 있음)
  is_active BOOLEAN NOT NULL DEFAULT true,  -- 삭제 대신 비활성화 (FK 무결성 보존)
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),

  -- 최소한의 정합성 보장 (완전한 해결은 아님)
  CONSTRAINT chk_category_fields CHECK (
    (category = 'TIME_BASED' AND total_minutes IS NOT NULL AND period_days IS NULL)
    OR
    (category = 'PERIOD_BASED' AND period_days IS NOT NULL AND total_minutes IS NULL)
  )
);
```

### `usage_sessions` — 개별 착석/이용 기록

```sql
CREATE TABLE usage_sessions (
  id UUID PRIMARY KEY,
  ticket_id UUID NOT NULL REFERENCES tickets(id),
  seat_id UUID,
  started_at TIMESTAMPTZ NOT NULL,
  planned_end_at TIMESTAMPTZ,   -- 시간권일 때만 값 존재
  ended_at TIMESTAMPTZ,
  status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
  bullmq_job_id VARCHAR(100)
);
```

### `product_history` — 상품 조건 변경 이력

```sql
CREATE TABLE product_history (
  id UUID PRIMARY KEY,
  change_group_id UUID NOT NULL,  -- 동시에 여러 필드가 바뀐 '한 번의 수정'을 묶는 그룹 id
  product_id UUID NOT NULL REFERENCES products(id),
  changed_field VARCHAR(30) NOT NULL,
  old_value VARCHAR(100),
  new_value VARCHAR(100),
  changed_by UUID NOT NULL,
  changed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  reason TEXT
);
```

## 6. 왜 스냅샷과 이력 테이블이 둘 다 필요한가

| 저장소                       | 답하는 질문                                                              |
| ---------------------------- | ------------------------------------------------------------------------ |
| **티켓의 스냅샷 컬럼**       | "이 특정 사용자와의 계약 조건이 뭐였는가?" (개별 계약 시점 고정값)       |
| **`product_history`** | "상품 라인 전체가 시간에 따라 어떻게 바뀌어왔는가?" (판매 정책 타임라인) |

- FK만 있으면: 상품 정의가 나중에 바뀔 때 이미 발급된 티켓도 같이 바뀌는 버그 발생
- 스냅샷만 있고 이력이 없으면: 특정 기간에 티켓이 안 팔렸을 경우 "그때 가격이 얼마였는지" 복원 불가

**판단 기준**: 상품 정의 중 "계약의 실체를 이루는 값"(가격, 총 시간, 유효기간)은 반드시 스냅샷. 상품 정의 중 "바뀌어도 기존 구매자에게 영향 없는 값"(설명 문구, 아이콘 등)은 FK만으로 충분.

## 7. 네이밍 컨벤션

| 레이어               | 컨벤션                                             | 예시                            |
| -------------------- | -------------------------------------------------- | ------------------------------- |
| DB 테이블/컬럼명     | `snake_case`                                       | `products`, `created_at` |
| JS/TS 변수/객체 속성 | `camelCase`                                        | `ticketProduct`, `createdAt`    |
| 경계(ORM 매핑)       | `@map`(Prisma), `name`(TypeORM) 옵션으로 자동 변환 | —                               |

PostgreSQL은 따옴표 없는 컬럼명을 자동 소문자화하므로, camelCase를 DB에 그대로 쓰면 매번 따옴표 처리가 필요해 번거로움.

## 8. 아직 다루지 않은 후속 주제 (필요 시 이어서 논의 가능)

- Outbox relay가 여러 인스턴스로 동시에 뜰 때 중복 처리 방지를 위한 락 전략
- 정기권에 "하루 최대 이용시간" 같은 부가 제약이 붙을 때의 스키마 확장
- 여러 테이블에 흩어진 감사 로그를 범용 `audit_log` 테이블로 통합할지 여부
- DB 트리거 자동 이력 기록 vs 애플리케이션 코드 명시적 기록
- 좌석 센서 없이 소프트웨어(하트비트 핑 등)만으로 착석 여부 판단하는 설계
