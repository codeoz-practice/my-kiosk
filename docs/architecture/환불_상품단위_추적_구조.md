# 환불을 상품(OrderItem) 단위로 추적하는 구조

`PaymentCancel`만으로는 "어느 상품이 환불됐는지"를 알 수 없었다.
`PaymentCancelItem`을 추가해 취소 요청과 상품을 연결한다.

## 기존 구조의 한계

```
Order 1:N OrderItem   (주문 상품)
Order 1:N Payment     (결제, 분할결제 지원)
Payment 1:N PaymentCancel  (PG 취소 요청)
```

`OrderItem`과 `Payment`/`PaymentCancel` 사이에는 직접적인 연결이
없다. 둘 다 `Order`를 거쳐야만 만난다. 그래서 "이 상품이
환불됐는가"라는 질문에 스키마가 답을 할 수 없었다. `PaymentCancel`은
"이 결제에서 얼마를 취소했다"는 금액만 알 뿐, 그 취소가 정기권
때문인지 시간권 때문인지는 기록되지 않는다.

매장별 상품 판매 순위처럼 "실제로 판매된 상품"을 집계하려면 환불된
상품을 제외해야 하는데, 이 연결이 없으면 정확한 집계가 불가능하다.

## 추가한 구조

```
Payment 1:N PaymentCancel            (기존)
PaymentCancel 1:N PaymentCancelItem  (신규)
OrderItem 1:N PaymentCancelItem      (신규)
```

`PaymentCancelItem`이 `PaymentCancel`과 `OrderItem`을 잇는 연결
모델이다. 상품별 취소 금액(`amount`)을 개별로 가지므로 다음을 모두
표현할 수 있다.

- 상품 1개 전액 취소
- 상품 1개 **부분** 취소 (예: 정기권 잔여기간 비례 환불)
- 다건 주문 중 **일부 상품만** 취소
- 다건 주문 **전체** 취소 (`PaymentCancel` 1건 + `PaymentCancelItem`
  여러 건)

```prisma
model PaymentCancelItem {
  id              String   @id @default(uuid())
  paymentCancelId String   @map("payment_cancel_id")
  orderItemId     String   @map("order_item_id")
  amount          Int      // 이 상품에 대해 취소된 금액(부분 취소 가능)

  paymentCancel PaymentCancel @relation(fields: [paymentCancelId], references: [id])
  orderItem     OrderItem     @relation(fields: [orderItemId], references: [id])
}
```

## 왜 `PaymentCancel`과 별개 모델로 나눴는가

**결제(Payment)는 "돈이 오간 사실"이고, 환불(Refund)은 "무엇에 대해
돈을 돌려주는가"라는 계약상의 판단이다.** 결제는 금전적 사건 하나라
쪼갤 이유가 없어 주문(Order) 단위로 한 번에 처리되지만, 환불 여부는
상품(OrderItem)마다 사정(사용 여부, 활성화 여부 등)이 달라 상품 단위로
결정된다. 이 비대칭이 `Payment`(Order 단위)와 `PaymentCancelItem`
(OrderItem 단위)이 서로 다른 계층에 존재하는 근본 이유이고,
`PaymentCancel`은 그 둘을 잇는 실행 기록(PG 취소 호출 1건)이다.

**결제(Payment)는 Order 단위로 실행된다.** PG 승인은 주문 전체
금액에 대해 한 번 이뤄진다. "이 상품이 어느 결제수단으로 결제됐는가"는
대부분 원천적으로 알 수 없고, 결제 시점에는 알 필요도 없다 (결제가
성공하면 주문 전체가 정상 판매된 것이므로).

> **정정**: 이 문단은 최초 작성 시 "분할결제(카드 30% + 현금 70%)도
> 지원해야 하므로 `Payment`가 `Order`에 붙는다"고 서술했으나,
> 분할결제는 이후 지원하지 않기로 확정되었다([TODO.md](../TODO.md)
> 참고). `Payment`가 `Order`에 1:N으로 붙는 실제 이유는 분할결제가
> 아니라 **결제 실패 후 재시도**뿐이다.

**환불은 상품(OrderItem) 단위로 결정되지만, 실행은 결제(Payment)
단위로 이뤄진다.** "이 상품만 환불해줘"라는 요구는 항상 상품
기준으로 시작되지만, 실제로 돈을 돌려주는 행위는 원래 그 돈이 들어온
결제수단으로 나가야 한다 (카드로 낸 돈은 카드로, 현금으로 낸 돈은
현금으로).

`PaymentCancel`(얼마를 어느 결제에서 취소했는지, PG 취소 API 호출
1건에 대응하는 금전적 실행 기록)과 `PaymentCancelItem`(그 취소가
어느 상품 몫이었는지, 환불을 처리하는 시점에 새로 결정되는 사실)을
분리한 이유가 이것이다. 정기권+시간권을 한 번에 환불 요청하면 PG
취소는 1건(`PaymentCancel` 1건)이지만, 그 안의 상품 내역은 2건
(`PaymentCancelItem` 2건)이 된다.

`OrderItem`에 직접 `Payment`를 연결하는 방향은 고려하지 않았다.
결제는 상품이 아니라 **주문(Order) 단위로 실행**되므로, `OrderItem`이
`Payment`를 직접 참조하면 같은 주문의 여러 상품이 같은 `paymentId`를
중복 저장하는 비정규화가 되어 `Order`를 거치는 경로를 우회하는 것에
지나지 않는다. 애초에 PG가 "이 승인 금액이 어느 상품 몫이다"라는
정보를 주지 않는 경우가 많아 구할 수 없는 정보이기도 하다.

> **정정**: 이 문단은 최초 작성 시 이 방향을 배제하는 근거로 "분할결제
> 시 그 연결은 M:N이 되어야 한다"는 점을 들었으나, 분할결제는 이후
> 지원하지 않기로 확정되어([TODO.md](../TODO.md)) 그 근거는
> 무효화되었다. 다만 분할결제 여부와 무관하게, 결제가 주문 단위로
> 실행되는 이상 이 방향 자체가 성립하지 않는다는 결론은 바뀌지 않는다.

## 업계 사례

Stripe의 `credit_note_line_item`, Shopify의 `RefundLineItem`이 같은
패턴이다. `Refund`(또는 `PaymentCancel`)는 취소 실행 사실만 기록하고,
별도의 line item 연결 모델이 "무엇을 취소했는지"를 담당한다.

이 프로젝트는 나이스페이/KCP/KSNET 등 국내 VAN사를 연동하므로,
국제 사례의 `Refund` 대신 국내 PG API 관례를 따라 `PaymentCancel`
이름을 유지했다.
