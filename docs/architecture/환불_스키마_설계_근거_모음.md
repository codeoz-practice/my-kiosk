# 환불 스키마 설계 근거 모음 — 헷갈리기 쉬운 것들

`RefundLock`, `PaymentCancelItem`을 다룰 때 반복적으로 헷갈리는 두 가지를
정리한다. 각 스키마의 전체 설계는 다음 문서에 있고, 이 문서는 그중 자주
재질문하게 되는 지점만 뽑아 근거를 모아둔다.

- [환불 동시 진행 방지 프로세스](./환불_동시_진행_방지_프로세스.md)

## 1. `RefundLock`에 `orderItemId`만으로 부족한 이유 — `paymentCancelId`가 왜 같이 있는가

```prisma
model RefundLock {
  orderItemId String @id @map("order_item_id")
  paymentCancelId String @map("payment_cancel_id")
  expiresAt DateTime @map("expires_at")
  ...
}
```

### 질문: `orderItemId`가 PK인데 `paymentCancelId`가 왜 또 필요한가?

**`orderItemId`는 "무엇이 잠겼는가"를 답하고, `paymentCancelId`는 "누가
잠갔는가"를 답한다.** 이 둘은 목적이 다르다.

- `orderItemId`(PK): 같은 상품에 대해 미해결 락이 두 개 이상 존재할 수
  없다는 유니크 제약. "지금 이 상품, 처리 중인가?"라는 질문에는 이것만
  있으면 충분하다.
- `paymentCancelId`: 락을 **해제**할 때, "내가 조금 전 획득한 바로 그
  락"인지 확인하는 소유권 토큰. "지금 걸려 있는 이 락이 내 것이 맞는가?"
  라는 질문에는 `orderItemId`만으로 답할 수 없다.

### 왜 소유권 확인이 필요한가 — 구체적 시나리오

[환불_동시_진행_방지_프로세스.md](./환불_동시_진행_방지_프로세스.md)의
TTL 설계 자체가 "서버가 락을 잡은 채로 응답 없이 멈출 수 있다"는 것을
전제로 한다. 이 전제 위에서 아래 순서가 실제로 벌어질 수 있다.

1. **요청 A**가 `orderItemId = X`에 대해 락 획득(`paymentCancelId = PC-1`).
   PG 호출 → 응답이 5분 넘게 지연(또는 서버가 그 사이 재시작).
2. TTL(5분) 만료. **요청 B**가 X를 다시 신청 → 만료된 락을 정리하고 새
   락 획득(`paymentCancelId = PC-2`) → PG 성공 → `PC-2` 확정 → 락 삭제
   (X는 다시 락 없는 상태).
3. 그 직후 **요청 C**가 X를 신청 → 새 락 획득(`paymentCancelId = PC-3`)
   → PG 호출 후 응답 대기 중.
4. 이때 **1번의 A가 뒤늦게 PG 응답을 받고 확정 처리를 재개**한다. `PC-1`을
   `SUCCEEDED`로 갱신하고 락을 지우려 한다.

이 시점에 A가 실행하는 삭제 조건이 `WHERE orderItemId = X`뿐이라면,
지금 X에 걸려 있는 건 **C의 락(PC-3)**인데 A가 그걸 자기 것인 줄
착각하고 지워버린다. 그러면 C가 아직 PG 응답을 기다리는 중인데 락이
사라지므로, 이 시점에 새 요청 D가 X에 대해 들어와도 막을 방법이
없어진다 — 이 문서 전체의 목적인 "동시 진행 방지"가 무너지는 지점이다.

`paymentCancelId`를 조건에 포함하면(`WHERE orderItemId = X AND
paymentCancelId = 'PC-1'`), A의 삭제 시도는 지금 X에 걸린 락이
`PC-3`이므로 조건에 맞는 행이 없어 **아무 일도 하지 않는다**(0 rows
affected). C의 락은 안전하게 보호된다.

이는 분산 락 패턴에서 "락을 걸 때 발급한 토큰과, 해제할 때 제시하는
토큰이 같은지 검증"하는 것(예: Redis 분산 락의 `SETNX` + unique value
검증)과 동일한 이유다.

### 비유: 사물함 열쇠

X번 사물함(`orderItemId`)을 여러 사람이 시간차를 두고 쓴다고 하자.

1. **A**가 X번 사물함을 쓰려고 열쇠를 받음(열쇠 번호 `PC-1`).
2. A가 너무 오래 걸려서, 관리자가 A의 열쇠를 무효화하고 사물함을 비움
   (TTL 만료).
3. **B**가 X번 사물함에 새 열쇠(`PC-2`)를 받아 씀 → 다 쓰고 반납 →
   사물함은 다시 빈 상태.
4. **C**가 X번 사물함에 또 새 열쇠(`PC-3`)를 받아 지금 쓰는 중.
5. 이때 **A가 뒤늦게 나타나** "나 다 썼어, 사물함 반납할게"라고 한다.

A가 들고 있는 건 `PC-1` 열쇠지만, 지금 X번 사물함에 꽂혀 있는 건
`PC-3`(C의 것)이다. 시스템이 "X번 반납 요청이니 X번 비워"라고만
처리하면 C가 아직 쓰고 있는데 사물함이 강제로 비워진다. 하지만 "네가
들고 있는 열쇠 번호(`PC-1`)가 지금 X번에 꽂힌 열쇠 번호(`PC-3`)와
같아?"를 먼저 확인하면, 다르므로 A의 반납 요청은 무시된다.
`paymentCancelId`가 바로 이 "내가 받았던 그 열쇠 번호"에 해당한다.

### 참고: `pgTransactionId`로 대체할 수 없는 이유

`PaymentCancel.pgTransactionId`는 PG 응답이 왔을 때 "어느 `PaymentCancel`
인지" 찾는 매칭 키이지, 락의 소유권 토큰이 아니다. 두 가지 이유로
`RefundLock`의 소유권 토큰 역할을 대신할 수 없다.

1. **시점이 다르다.** 락은 PG를 호출하기 **이전**(`PaymentCancel` 생성
   직후)에 건다. 이 프로젝트의 현재 구현(`PaymentService.requestPayment`
   패턴)은 PG사가 승인/취소 후 돌려주는 응답값으로 `pgTransactionId`를
   채운다 — 즉 락을 거는 시점에는 아직 `null`이라 애초에 쓸 수 없다.
   (참고: PG 프로토콜에 따라 가맹점이 먼저 채번해 요청에 실어 보내고
   PG가 그대로 돌려주는 방식도 있으나, 이 프로젝트는 그 방식을 쓰지
   않는다 — `pgTransactionId String? @unique`로 nullable인 것이 그 근거.)
2. **역할이 다르다.** `pgTransactionId`는 PG(외부 시스템) 관점의
   거래 식별자이고, `paymentCancelId`는 우리 시스템 내부의 취소 시도
   레코드(PK)다. 내부 PK가 이미 있는데 외부 시스템 식별자를 소유권
   토큰으로 쓰면, PG 연동 방식이 바뀔 때(예: 가맹점 채번 방식으로 전환)
   락 테이블 스키마까지 영향을 받는 불필요한 결합이 생긴다.

### 부수 효과: `PaymentCancel 1:N RefundLock`도 이걸로 자연스럽게 설명된다

하나의 `PaymentCancel`이 여러 상품(정기권+시간권 동시 취소)을 묶으면,
그 여러 `RefundLock` 모두 "같은 `PaymentCancel`에 속한 락들"이어야
한다. 이건 `orderItemId`만으로는 표현할 수 없고, `paymentCancelId`가
있어야 "이 락들이 한 취소 요청에 묶여 있다"는 관계를 표현할 수 있다.

## 2. `PaymentCancelItem`을 중간 테이블로 둔 이유

```
Payment 1:N PaymentCancel            (결제 단위)
PaymentCancel 1:N PaymentCancelItem  (중간 테이블)
OrderItem 1:N PaymentCancelItem      (상품 단위)
```

### 질문: 이 구조가 지나치게 복잡해 보이는데, 업계 표준인가 기존 구조를 유지하려는 타협인가?

**결제(Payment)와 환불(Refund)은 원래 단위가 다르다.** 이게 이 구조가
필요한 근본 이유다.

> **결제(Payment)는 "돈이 오간 사실"이고, 환불(Refund)은 "무엇에 대해
> 돈을 돌려주는가"라는 계약상의 판단이다.**

- 결제는 금전적 사건 하나라 쪼갤 이유가 없다. PG 승인은 주문
  전체 금액에 대해 한 번 이뤄지므로 `Payment`는 **주문(Order) 단위**로
  존재한다.
- 반면 환불 여부는 상품마다 사정이 다르다(이 프로젝트 기준: 정기권은
  활성화 여부, 시간권은 사용량). 그래서 환불 결정은 **상품(OrderItem)
  단위**로 이뤄진다.

이 "결제=Order 단위 / 환불 판단=OrderItem 단위"라는 비대칭이 있는 한,
그 둘을 잇는 연결 모델은 순수 도메인 모델링 관점에서도 필요하다 —
기존 구조를 억지로 유지하기 위한 타협이 아니라, 이 비대칭 자체가
연결 모델을 요구한다.

### 왜 M:N이 되는가

- `PaymentCancel`(취소 실행 기록, PG 취소 API 호출 1건)은 여러 상품을
  한 번에 묶어 취소할 수 있다 — 정기권+시간권을 함께 환불하면
  `PaymentCancel` 1건에 상품 2건이 딸린다.
- `OrderItem`(상품 1건)은 잔여 사용량 비례 환불처럼 **여러 번에 걸쳐
  나눠 취소**될 수 있다 — 부분 환불 여러 건이면 `PaymentCancelItem`이
  같은 `orderItemId`로 여러 건 쌓인다.

두 방향 모두 1:N을 넘어서므로, 관계 자체가 M:N이고 이를 표현하려면
연결 테이블이 필요하다. `PaymentCancelItem`이 `amount`(상품별 취소
금액)를 개별로 갖는 것도 이 M:N을 구체적인 금액 단위로 쪼개 기록하기
위함이다.

### 왜 `OrderItem`이 `Payment`를 직접 참조하지 않는가

"연결 모델 없이 `OrderItem`에 `paymentId`를 직접 두면 안 되나?"라는
질문이 나올 수 있는데, 이 방향은 애초에 성립하지 않는다. 결제는
상품이 아니라 **주문 단위로 실행**되므로, `OrderItem`이 `Payment`를
직접 참조하면 같은 주문의 여러 상품이 같은 `paymentId`를 중복 저장하는
비정규화가 될 뿐이다 — `Order`를 거치는 정상 경로를 우회해서 같은
정보를 한 번 더 저장하는 것에 지나지 않는다. 게다가 PG가 "이 승인
금액이 어느 상품 몫이다"라는 정보를 애초에 주지 않는 경우가 많아,
결제 시점에는 구할 수조차 없는 정보이기도 하다.

> **참고**: 이 문서의 초안 단계에서는 "분할결제(카드 30% + 현금 70%)
> 지원 때문에 M:N이 필요하다"는 근거를 들었으나, 분할결제는 이후
> 지원하지 않기로 확정되었다([TODO.md](../TODO.md)). 그러나 분할결제
> 여부와 무관하게 "결제=Order 단위, 환불 판단=OrderItem 단위"라는
> 비대칭 자체는 그대로이므로, `PaymentCancelItem`이 필요하다는 결론은
> 바뀌지 않는다. 분할결제 폐기가 실제로 무효화한 것은 "`Order:Payment`가
> 왜 1:N인가"의 근거뿐이다 — 지금은 분할결제가 아니라 **결제 실패 후
> 재시도**가 그 유일한 이유다.

### 업계 사례와의 비교

같은 비대칭을 겪는 결제 시스템은 공통적으로 이 패턴을 쓴다.

| 서비스 | 결제/승인 (상위 단위) | 환불 연결 모델 (상품 단위) |
|---|---|---|
| Stripe | `Charge`/`PaymentIntent` | `credit_note_line_item` |
| Shopify | `Transaction` | `RefundLineItem` |
| 이 프로젝트 | `Payment` | `PaymentCancelItem` |

"연결 모델을 별도로 둔다"는 해법 자체는 업계 표준이고, 이 프로젝트가
그 표준을 특이하게 비튼 것이 아니라 그대로 따른 것이다. 다만 국내 PG
(나이스페이/KCP/KSNET)는 부분취소를 PG API 레벨에서 지원하므로,
`PaymentCancel`(PG에 실제로 보내는 취소 요청 단위)과
`PaymentCancelItem`(그 취소의 내부 상품별 귀속)을 분리하는 것이 국내
PG 연동 방식에도 자연스럽게 들어맞는다.
